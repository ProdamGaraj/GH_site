# Запросы привязок данных: архитектура (этап 0)

Статус: согласовано владельцем 2026-11-18 (решения — раздел 7). Реализация — этапами 1, 3, 4, 5
(этап 2 — SQL — позже). Предыдущий шаг (этап A, закрытие дыр в
`/api/data/submit`) уже написан и служит фундаментом.

## 1. Цель

Любая отправка данных с сайта — в любой внешний сервис, любым методом
(включая GET) — настраивается в привязке редактора и выполняется так:

```
браузер ──(id привязки + данные)──▶ наш сервер ──(запрос по шаблону)──▶ внешний сервис
        ◀──(разрешённые поля ответа)──          ◀────────(ответ)────────
```

Сервер контролирует каждый шаг: проверка, сборка запроса, авторизация,
журнал, повторы, что вернуть посетителю. Браузер не знает адреса, токена,
метода и формы запроса.

Первый коннектор — REST. Архитектура рассчитана на GraphQL, SQL и прочие типы
источников: они добавляются коннектором, без изменения конвейера, рантайма
страницы и очереди.

## 2. Инварианты безопасности (не обсуждаются, проверяются тестами)

1. Адрес, метод, заголовки, авторизация и форма запроса — только из сохранённой
   привязки и её источника. Из браузера: `outputBindingId`, `data` (значения
   полей), `trigger`. Всё прочее — 400 (уже так, этап A).
2. Данные посетителя подставляются в запрос **структурно**, не склейкой текста:
   в JSON — значением узла, в путь URL — `encodeURIComponent`, в query —
   через `URLSearchParams`, в заголовок — без CR/LF. Посетитель не может
   добавить поле в тело, сменить путь или заголовок.
3. Секреты (токены, пароли источника) не попадают ни в журнал, ни в очередь,
   ни в ответ браузеру, ни в превью редактора. Подставляются в момент отправки.
4. Посетитель получает только поля ответа, явно разрешённые в привязке. По
   умолчанию — ничего, кроме статуса.
5. Исходящие запросы — только через защищённый клиент (SSRF-guard) с таймаутом.
6. Повтор отправки никогда не идёт, пока предыдущая попытка ещё в пути.

### 3.1 Спецификация запроса (`RequestSpec`) — хранится в привязке

`outputConfig.request` — данные, не код. Общая часть + часть коннектора:

```ts
interface RequestSpec {
  version: 1
  connector: 'rest'            // 'graphql' | 'sql' | … — позже
  rest?: RestRequestSpec       // часть коннектора; у graphql — свой ключ и т.д.
  response?: ResponseSpec      // что вернуть странице
  delivery?: DeliverySpec      // прямо или через очередь
  dedupe?: DedupeSpec          // этап 5
}

interface RestRequestSpec {
  method: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'
  path: TemplateString                       // '/clients/{{form.id}}' — к url источника
  query?: Array<{ key: string; value: TemplateValue }>
  headers?: Array<{ key: string; value: TemplateString }>
  body?: { format: 'json'; value: TemplateValue }
       | { format: 'form-urlencoded'; fields: Array<{ key: string; value: TemplateValue }> }
       | { format: 'none' }
}
```

`connector` по умолчанию берётся из типа источника (`rest-api` → `rest`), но
хранится явно: привязка самодостаточна, и смена типа источника не ломает
молча сохранённый запрос.

### 3.2 Шаблоны (`TemplateEngine`) — общий для всех коннекторов

Шаблон — JSON-дерево (а не текст), листья которого могут ссылаться на данные:

| В шаблоне | Результат |
|---|---|
| `"{{form.phone}}"` — лист целиком ссылка | значение **с типом** (строка, число, массив, объект) |
| `"Имя: {{form.name}}"` — ссылка внутри текста | строка |
| `["{{form.phone \| digits}}"]` | массив из одной строки (`phones: [...]` MacroCRM) |
| `{"utm": {"source": "{{visitor.utm.source}}"}}` | вложенный объект |
| `42`, `true`, `"buy"` | константа |

Пространства имён ссылок (контекст `RequestContext`):

| Ссылка | Откуда | Доверие |
|---|---|---|
| `form.*` | поля формы / `data` запроса | данные посетителя |
| `page.path`, `page.lang`, `page.title` | присланы рантаймом, длины ограничены | данные посетителя |
| `visitor.utm.*`, `visitor.referrer` | присланы рантаймом | данные посетителя |
| `request.ip`, `request.domain`, `request.userAgent` | сервер | сервер |
| `now`, `now.date` | сервер | сервер |
| `lead.*` и другие провайдеры | `ContextProvider` (этап 5: каталог, путь посетителя) | сервер |

Фильтры (короткий фиксированный список, без выполнения кода):
`default:"…"`, `trim`, `digits`, `number`, `bool`, `lower`, `upper`, `json`.
Отсутствующее значение без `default` — `null` в JSON, пустая строка в тексте;
обязательность проверяет валидация, а не шаблон.

Парсер шаблона — свой, маленький, с тестами на каждую ветку; `eval` и
`safeExpression` здесь не используются.

### 3.3 Коннектор (`Connector`) — точка расширения

```ts
interface Connector<Spec> {
  id: 'rest'                                       // 'graphql', 'sql', …
  sourceTypes: string[]                            // ['rest-api', 'rest']
  /** Проверка спецификации при сохранении в редакторе и при отправке. */
  validate(spec: Spec): SpecIssue[]
  /** Шаблон + контекст → конкретный запрос (без секретов). */
  prepare(spec: Spec, ctx: RequestContext, source: SourceInfo): PreparedRequest
  /** Что показать в превью редактора и записать в журнал (секреты скрыты). */
  describe(prepared: PreparedRequest): RequestDescription
  /** Выполнить: авторизация подставляется здесь. */
  execute(prepared: PreparedRequest, auth: AuthConfig | undefined, signal: AbortSignal): Promise<ConnectorResult>
}

interface ConnectorResult {
  ok: boolean
  status?: number
  data?: unknown
  /** Можно ли повторить: 'safe' — точно не дошло; 'unknown' — могло дойти; 'never'. */
  retry: 'safe' | 'unknown' | 'never'
  error?: { code: string; message: string }   // только для журнала
}
```

`ConnectorRegistry` сопоставляет тип источника и коннектор. В
`dataSourceRuntime.ts` у дескриптора типа появляется признак `connector`
(есть ли отправка). Редактор показывает «Запрос» только для типов с
коннектором; для остальных — «отправка для этого типа пока не поддерживается».

REST-коннектор переиспользует `SecureDataSourceService` (SSRF-guard, авторизация
bearer / api-key / basic / oauth2 / macro-hmac, TLS-опция) — новый HTTP-клиент
не пишется.

Классификация повторов REST: сеть до соединения (DNS, отказ соединения) —
`safe`; таймаут и 5xx — `unknown`; 408 и 429 — `safe`; прочие 4xx — `never`.

### 3.4 Ответ странице (`ResponseSpec`)

```ts
interface ResponseSpec {
  expose: 'status' | 'fields'          // по умолчанию 'status'
  dataPath?: string                    // 'data.items'
  fields?: Array<{ from: string; to: string }>   // 'price.total' → 'price'
  maxItems?: number                    // если по пути массив; по умолчанию 50
  variable?: string                    // переменная страницы для данных (обязательна при 'fields')
}
```

Сервис ответил — посетитель получает `{ status: 'done', data, variable }` только
из перечисленных полей; рантайм кладёт `data` в переменную страницы
(`$var(variable)` — её читают привязки «Получение» с источником page-variable) и
шлёт событие `vcms:response`. Ошибка сервиса — наше сообщение и код, детали —
в журнал.

Ответы `/api/data/submit`: 200 `done`; 400 `INVALID_INPUT` (данные посетителя не
годятся для запроса — например, сегмент пути «..»: URL-парсер понял бы его как
переход по папкам); 404 `FORM_NOT_CONFIGURED`; 502 `DELIVERY_FAILED`.

### 3.5 Доставка (`DeliverySpec`) — очередь включается вручную

```ts
interface DeliverySpec {
  mode: 'direct' | 'queued'            // по умолчанию 'direct'
  timeoutMs?: number                   // одна попытка; по умолчанию 15 000
  waitMs?: number                      // queued: сколько ждёт посетитель; 8 000
  retry?: {
    maxAttempts: number                // queued: по умолчанию 5
    backoffSec: number[]               // [60, 300, 1800, 7200, 21600]
    retryUnknown: boolean              // повторять при «могло дойти» (таймаут, 5xx); по умолчанию false
  }
}
```

- **direct** (по умолчанию, в т.ч. для GET): одна попытка, посетитель ждёт
  ответа до `timeoutMs`, без повторов. Запись в журнале есть всегда.
- **queued**: запрос записывается до отправки → первая попытка сразу →
  посетитель ждёт до `waitMs`:
  - сервис ответил вовремя → `done` (+ разрешённые поля);
  - не успел → `accepted`, попытка продолжается, повторы — фоном;
  - явный отказ (`never`) → `failed`, без повторов.

Ответы рантайму: `{ status: 'done' | 'accepted' | 'failed', submissionId, data?, error? }`.
У каждого статуса в редакторе — своё действие (сообщение, редирект, сброс
формы, вставка данных в элементы).

### 3.6 Очередь и журнал (`RequestJobStore`, `RequestWorker`)

Одна таблица на журнал и очередь — расширение `data_submissions` (одна строка
на запрос, не на попытку):

| Колонка (новая) | Назначение |
|---|---|
| `deliveryMode` | direct / queued |
| `request` jsonb | собранный запрос без секретов — его и переотправляем |
| `attempts`, `maxAttempts` | счётчик |
| `nextAttemptAt` | когда следующая попытка |
| `lockedUntil` | аренда: попытка в пути, второй никто не возьмёт |
| `retryUnknown` | снимок политики на момент отправки |
| `response` jsonb | разрешённая часть ответа (обрезанная) |
| `lastError` | для журнала |

Статусы: `pending` → `in_flight` → `done` | `failed` | (снова `pending` с
`nextAttemptAt`) ; `timeout` → по политике `retryUnknown`.

- Переотправляется **снимок** запроса, собранный при отправке: правка привязки
  не меняет уже принятые запросы. Токен — свежий из источника.
- `RequestWorker` — в процессе бэкенда, раз в 15 с: берёт задачи
  `SELECT … FOR UPDATE SKIP LOCKED` с `nextAttemptAt <= now` и истёкшей
  арендой, ставит аренду `now + timeout + запас`, отправляет. Безопасен при
  нескольких экземплярах бэкенда; после падения процесса задача вернётся по
  истечении аренды.
- Хранение: тело запроса содержит персональные данные — срок хранения в
  журнале ограничен (вопрос 3 ниже), потом тело стирается, строка остаётся.

### 3.7 Рантайм страницы

Один контракт для всех привязок: `POST /api/data/submit` →
`{ status, submissionId, data?, error? }`.

- Собирает значения полей (FormData / элемент), `page.*`, `visitor.*`
  (UTM, реферер — тот же учёт, что у рантайма заявок; без дублирования кода).
- Маппинг полей уходит на сервер (шаблон). В браузере остаются только
  проверки для удобства посетителя; решающая проверка — на сервере.
- Выполняет действия статуса `done` / `accepted` / `failed`, вставляет
  разрешённые поля ответа в элементы или переменные страницы (`$var`).
- В превью редактора реальная отправка не идёт (этап 4): ответ-заглушка и
  пометка «предпросмотр».

### 3.8 Редактор

Вкладки привязки: **Триггер · Запрос · Ответ · Доставка · Валидация · Действия · Журнал**
(этап 1: Триггер · Запрос · Ответ · Валидация · Действия; «Маппинг» заменён
шаблоном тела в «Запросе»).

- **Запрос**: метод, путь, query, заголовки, тело (JSON с подсветкой ссылок
  или поля формы-urlencoded); справа — список доступных ссылок (поля формы
  блока, `page.*`, `visitor.*` …), клик вставляет ссылку.
- **Превью**: `POST /api/data/bindings/:id/preview` с примерными значениями →
  «что уйдёт» (метод, адрес, заголовки без секретов, тело) — тем же кодом, что
  в бою.
- **Тест-отправка**: тот же конвейер с сессией редактора, ответ сервиса
  целиком (редактору можно).
- **Журнал**: запросы привязки — статус, попытки, ошибка, время.

### 3.9 Чтение с данными посетителя («Получение»)

Поиск, фильтры, «узнать цену»: запрос к сервису зависит от того, что ввёл
посетитель. Тот же `RequestSpec` и `TemplateEngine`, но другие правила — чтение
должно быть быстрым, после него идут серверные трансформации:

- **Никогда не через очередь.** У чтения нет `delivery`: одна попытка, таймаут
  короче (по умолчанию 8 с). Опоздавший ответ никому не нужен.
- **Привязка без ссылок на данные посетителя** работает ровно как сейчас
  (`fetch-with-transforms`, кеш источника) — ни одной лишней операции.
- **С параметрами посетителя**: шаблон → готовый запрос → тот же
  `CachedDataSourceService` (ключ кеша = источник + адрес + query + тело, к ним
  добавляются заголовки) → трансформации привязки → ответ.
  - Кеш — только если у источника задан `cacheTTL`. Разных ключей от
    посетителей много: память ограничена размером кеша (вытеснение старых), а
    одинаковые одновременные запросы склеиваются в один (`inflight` уже есть).
  - Привязка может запретить кеш ответов с параметрами посетителя (личные
    данные: «мои заявки», «мой баланс»).
- **Кеш результата после трансформаций** (экономит CPU, а не сеть) — не
  делаем вслепую: сначала замер времени трансформаций в журнале, потом решение.
- В журнал чтения пишутся только сбои и медленные запросы, не каждый успешный
  запрос (иначе журнал раздувается от каждого показа страницы).

## 6. Тесты (обязательный минимум)

- `TemplateEngine`: каждая форма ссылки и каждый фильтр; попытки инъекции
  (`"`, `}}`, `\r\n`, `../`, `?a=`) в значениях; отсутствующие значения.
- REST-коннектор: сборка URL / query / заголовков / тела всех форматов; секреты
  не в `describe`; классификация повторов.
- Конвейер: direct и queued; ответ вовремя / поздно / отказ; разрешённые поля.
- Очередь: два воркера не берут одну задачу; аренда после падения; повтор не
  идёт при `retryUnknown: false`; лимит попыток.
- Рантайм страницы (jsdom): статусы, действия, вставка ответа.
- Редактор (vitest): Запрос / Ответ / превью.
- Адаптер старых привязок: старый формат даёт тот же запрос, что раньше.
